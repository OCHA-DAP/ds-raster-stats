Lineage: the 2024 optimization, and this one

The team's 2024 methodology work (retired Confluence, "Raster Statistics → Methodology") already made one big jump: rasterizing admin boundaries once per country/level and reusing the mask across dates, instead of re-rasterizing per date as baseline python-rasterstats does. Their benchmarks: Ethiopia at 125 dates went from 6.6 s to 0.75 s (~9×), the Philippines from ~35 s to ~0.2 s — but cost still grew linearly with the number of polygons (measured to ~90). PR #49 is the next step in the same direction: precompute not just the mask but the full pixel-coverage weight matrix, compute all slices at once, and cache the matrix on disk.

On accuracy, the 2024 page chose 0.05° nearest-neighbour upsampling explicitly as "a simplified approach for weighting the input pixels by the amount of area covered", and measured that its error against exactextract ground truth grows with the upsampled resolution (RMSE ≈ 0.07 at 0.05° on the Philippines ADM2 case), with finer resolutions rejected for memory/performance. exactextract itself was rejected as "much slower to run repeated calculations" — true when invoked per date. Used once per country to build weights, its cost is a one-off ≤ 0.4 s, and the per-date math is faster than the whole-pixel path — so the 2024 accuracy/performance trade-off no longer exists. In a comparison against prod values (BDI/NGA/TCD, one issuance, 6,475 rows) the median mean-difference vs the legacy method was 0.25%, with larger differences confined to the smallest polygons — the same distribution the 2024 Philippines histogram documented as the legacy method's approximation error.

Notes & caveats

  • What's excluded: DB writes (identical code path in both methods) and COG stack setup (46 s on job compute for the 700-COG chunk, shared). Charts show the per-country stats path only.
  • The archival bottleneck is now I/O, not compute. Each country's clip pulls windows from all 700 remote COGs (~62 s/country on Azure, ~125 s from a home connection) because the SEAS5 stack is lazy — unlike the other datasets, it is never persisted at stack time. After the method change this fetch is 94% of the new method's per-country time (Burundi: 61 s fetch vs 3.8 s stats), so persisting the chunk stack once is now the single highest-value follow-up; the DB write path (COPY-staging upsert) is the other.
  • Threading the COG opens was measured, found useless, and removed. No gain on a home connection (SEAS5 49 COGs: 6.2 s serial vs 6.1 s threaded) and none on Azure-internal job compute either (SEAS5 7 issuances: 7.9 s serial vs 8.2 s threaded; IMERG: 0.79 vs 0.81 s per COG). The reason is structural rather than about the network: open_rasterio(…, chunks="auto") only reads metadata, so the bulk transfer happens later, per country, in the clip step. The PR reverted the threading rather than ship unmeasured concurrency.
  • Machines: Databricks job compute (Standard_DS4_v2, 8 cores, Linux, Python 3.10) — the environment the pipeline actually runs in, and the headline numbers here — and an Apple Silicon laptop (10 cores, macOS 14.5, Python 3.12) for comparison. Both single-process. The cluster node is ~3–20× slower in absolute terms and the legacy method degrades furthest on it, which is why the same change is worth more in production than on a laptop.
  • An environment bug the cluster run surfaced: affine ≥2.4 puts a cached_property on a __slots__ namedtuple, which raises on Python 3.10 (the Databricks 14.3 runtime) whenever a rasterio transform is indexed — harmless on 3.12. The PR pins affine==2.3.1. The same run also caught a relative .cache/ default that the Databricks workspace filesystem rejects; caches now default under the system temp dir.
  • Data: prod SEAS5 monthly precip COGs + Fieldmaps COD boundaries from the prod polygon container. Scenario B chunk: issuances 2016-01…2024-04. "Warm" = weight matrices already on disk; "cold" includes the exactextract build.
